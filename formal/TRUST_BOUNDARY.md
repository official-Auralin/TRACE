# Trust boundary and evidence ledger

## Mathematical statement

All local mathematical claims listed in `PROOF_COVERAGE.md` are checked by Lean's kernel from source. The build allows only Lean's ordinary foundational `propext`, `Classical.choice`, and `Quot.sound` dependencies, and records the complete named-theorem dependency inventory. There are no admitted proof obligations or custom axioms in these sources. This is a statement about the formalized finite contract, not a guarantee that every possible informal interpretation of “cause” or “strategy” has been captured.

## Concrete release certificate checking

The independent Lean runner consumes actual public item JSON and the same version-2 game certificates used by Python. For each item it checks dimensions, binary values, total transitions, exact semantics text/version, actual replay, every local recurrence equation, query coverage, failure witnesses, and strict answer shape. Canonical key injectivity, checked-root insertion, lookup binding, and required-query coverage are now proved in `QueryLookup.lean`. Its lookup and coverage definitions are used directly by the runtime. They establish equivalence to the reference `finiteBad` decision without recomputing that recursive oracle. Thus the source solver and submitted table are not trusted to supply correct labels; the remaining adapter wiring is explicit below.

A true table root needs a replayed witness as an additional diagnostic, while a false root is established by the full table. Absence claims never follow merely from failure to find a path. Canonical tables exist for every finite typed instance, so the table-checking criterion is complete as well as sound. Malformed required semantic fields are outside that completeness claim and are rejected by the adapter. The native decoders can ignore extra object fields; strict rejection of unsupported dataset targets or constraints belongs to the Python import boundary, not a general native JSON theorem.

The following boundaries remain trusted, explicit, and separately tested:

1. **Input interpretation and adapter wiring.** Lean's JSON parser and the adapters turn byte strings into a typed machine, finite cells, actual input, and Boolean tables. Structural bounds and exact semantic tags are checked, but a theorem over serialized JSON bytes has not been supplied. Numeric column encoding is checked to be a complete bijection in the certificate adapter; invalid machine indices and dimensions are rejected before modulo/default indexing is used. The pure query-map helpers are proved, while the `Except`/IO control flow that validates each record and accumulates its checked roots remains tested adapter code. There are no fixed small mathematical size caps.
2. **Record identity.** The Lean runner checks that `instance_sha256` is a well-formed lowercase digest but does not implement SHA-256 or Python's canonical JSON serialization. The verification orchestrator must run Python's canonical public-item digest equality before passing each record. A standalone Lean runner pass certifies the supplied item/certificate semantics, not that a digest names a separately held item.
3. **Execution platform.** Lean kernel correctness, Lean's executable evaluator/compiler, standard library runtime, operating system, and hardware are trusted. The generic proofs do not use `native_decide` or a compiler-trust axiom. Executing a proved Boolean decision on a JSON instance still relies on the runtime; it is not a separately emitted per-instance kernel proof term.
4. **Semantic construction versus its presentation.** `compileRoundReduced`, called by the actual CLI, has general all-input/all-round output and state preservation theorems. `compileTerminal`, also called by that CLI, projects the target round to its output and reduces equal branches. Its typed display semantics preserves the target, G∧P and every inclusion-minimal explanation while using unchanged semantic routing at earlier rounds. It deliberately omits the irrelevant post-target successor from the terminal display; the semantic forest still retains it. Assembly and JSON serialization of the two forests remain tested adapter operations. Python, JavaScript interpretation and drawing, server access control, agent adapters, and interface wording are validated by independent checks and tests. In particular, rendering all true terminal outcomes as one unmistakable target and all false outcomes as failure is an application obligation, not a consequence of the typed-tree theorem or evidence of participant comprehension.
5. **Study validity.** Proofs establish task semantics and the stated finite decision procedure. They do not establish participant comprehension, construct validity, recruitment adequacy, psychometric reliability, model fairness, consent, approvals, or empirical findings.

6. **Static lab demo.** The public `trace.demo.v1` artifact reuses the certified boards and implements grading in JavaScript for execution without a collection backend. The generic mathematical recurrence remains the same, but this JavaScript port, local persistence and UI are separately tested trusted code, not a proved extraction of Lean. Cross-language and small exhaustive checks do not imply a kernel proof over all JavaScript executions. Public tasks, executable solvers and locally editable progress cannot establish unassisted human performance or authenticated outcomes; hosted collection and a new learning-enabled study protocol are a separate milestone.

## Strategy scope

`WinningWordPolicy` is the bounded game contract with candidate fixed before play: challenger chooses G/P; G gives challenger every unfixed input choice; P gives explainer every selected input choice; controller transitions are forced. The theorem proves its quantified winning condition and its absorbing min-even encoding. Reconstructing an original synthesis arena, reopening controller choices, translating arbitrary temporal formulas, and proving full-policy necessity require a different contract and additional proof obligations. TRACE's finite formal certificate does not claim these extensions.

## Reproducibility

`verify.sh` discards all previous local `.olean` build products and recompiles both vendored and new source with Lean 4.24.0. `proof_checks.json` records compiler, source, and native executable hashes, theorem counts, and the axiom report hash. Detailed C/object/Lean products and the axiom inventory stay under ignored `.build`; release certificate records can be streamed and need not be persisted in the source tree. `PROVENANCE.json` identifies the preserved foundation copies. The project-wide verification report separately records concrete-data checks and negative/mutation tests. Neither a source hash nor a successful proof build substitutes for a concrete-data run.

The archived v3 board-first compiler and renderer were outside the Lean theorem inventory. The current general semantic constructor and terminal display projection have kernel-checked correspondence theorems. The earlier v4 display retained separate terminal bulbs for state-distinct transitions with identical outputs; that representation could pass execution checks while misleading participants about the scored goal. Projection correctness repairs the semantic distinction; separate visual checks and comprehension trials must assess the rendered meaning. Exhaustive tests on deliberately small examples continue to detect parser, array assembly, serialization, and browser mistakes; they are not the basis of the general theorem. Large finite construction and grading do not require enumerating every input word or every answer.
